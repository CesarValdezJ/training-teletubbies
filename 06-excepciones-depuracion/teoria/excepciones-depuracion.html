excepciones · 01

¿Qué es una excepción?

Un evento que interrumpe el flujo normal del programa cuando algo sale mal: un archivo que no existe, un dato inválido, una división entre cero. Java la lanza (throw) y busca hacia arriba en la pila de llamadas quién la atrape (catch); si nadie lo hace, el programa termina y muestra el stack trace. No son para el flujo normal (lista vacía, "no encontrado") — eso se modela con un valor de retorno.

checked — extends Exceptionunchecked — extends RuntimeException
¿el compilador obliga?Sí — throws o catchNo
para quéCondición esperable que quien llama puede manejar: archivo no existe, red caídaError de programación o contrato roto: argumento nulo, índice fuera de rango, división entre cero
ejemplos del JDKIOException, SQLExceptionNullPointerException, IllegalArgumentException, ArithmeticException
excepciones · 01

try · catch · throw · throws

double parseQty(String text) throws InvalidQtyException { // throws: la puede propagar if (!text.matches("\\d+")) throw new InvalidQtyException(text); // throw: la lanza aquí y corta el flujo return Integer.parseInt(text); } try { // try: código que podría fallar total += parseQty(line.qty()); } catch (InvalidQtyException e) { // catch: la maneja si se lanza System.out.println("skipping line: " + e.getMessage()); }
  • throw lanza una excepción (una instancia) en ese punto · throws va en la firma y declara qué checked puede propagar el método
  • try envuelve el código riesgoso · catch lo captura por tipo · finally / try-with-resources cierran recursos pase lo que pase

Ignorar el error vs. definir el contrato

} catch (Exception e) { } // ignorado en silencio: se pierde qué pasó } catch (IOException e) { throw new OrderProcessingException("cannot read order " + id, e); }

La versión de abajo declara un contrato de error del dominio y conserva la causa. Quien llama decide qué hacer.

excepciones · 01

¿Cuándo crear una excepción propia?

Cuando el error es parte del vocabulario del dominio y quien llama necesita distinguirlo de otros.

public class NoGradesException extends RuntimeException { public NoGradesException(String who) { super("'" + who + "' has no grades to average"); } }
  • Nombre que se lee como frase: NoGradesException, OrderTooLargeException.
  • Mensaje con el dato concreto que falló, no "error genérico".
depuración · 02

¿Qué es depurar (debugging)?

Encontrar la causa de un defecto y corregirla — no solo tapar el síntoma. Se hace cuando el programa no hace lo que esperas: lanza una excepción, o devuelve un resultado incorrecto sin fallar. Cambiar código al azar es lento y poco confiable; conviene seguir siempre el mismo método:

1 · reproducirencuentra la entrada mínima que dispara la falla. sin esto no puedes arreglar ni verificar.
2 · aislarreduce el área sospechosa: breakpoint, bisección, quitar partes.
3 · hipótesis"creo que x es null aquí porque...". una a la vez.
4 · verificarconfírmala o descártala con el debugger o una prueba. repite.
depuración · 02

Leer un stack trace

exception in thread "main"
java.lang.NullPointerException: Cannot invoke "List.iterator()" because the return value of "Student.getGrades()" is null at GradeCalculator.studentAverage(GradeCalculator.java:18) <- primera línea de tu código at GradeCalculator.classAverage(GradeCalculator.java:29) at Main.main(Main.java:15)
  • La primera línea ya dice qué es null y por qué.
  • La primera at de tu código (no del JDK) suele ser el punto de la falla.
  • Caused by: es la causa raíz — léela hasta el fondo.
depuración · 02

El debugger le gana a println

  • Breakpoint + inspección de variables: ves todo el estado, no solo lo que se te ocurrió imprimir.
  • Step over (siguiente línea) · step into (entrar al método) · step out (salir).
  • Watch / evaluate: evalúa cualquier expresión en el punto de pausa.
  • Breakpoint condicional: para cuando i == 37, sin detenerse 36 veces antes.
código limpio · 03

Prácticas de código limpio

Nombres que revelan la intencióndaysSinceLastLogin, no d. El nombre reemplaza al comentario.
Funciones pequeñas, una sola cosaSi necesitas "y" para describir qué hace, divídela. Sin anidar if tras if: valida y sal temprano.
No te repitas (DRY)La misma lógica en dos lados tarde o temprano cambia en uno solo.
Que el código se explique soloComenta el porqué, no el qué. Borra el código muerto.
Pocos parámetros0–2 idealmente. Muchos argumentos suelen esconder un objeto que falta.
Manejo de errores explícitoExcepciones claras y constantes con nombre, en vez de null, códigos o números mágicos.

Objetivo común: que quien lo lea después — tú, en un mes — lo entienda a la primera.

pruebas junit 5 · 04

Anatomía — Arrange · Act · Assert

@Test void studentAverage_returnsMeanOfGrades() { // Arrange Student ana = new Student("Ana", List.of(7.0, 8.0, 9.0)); // Act double average = calculator.studentAverage(ana); // Assert assertEquals(8.0, average, 1e-9); }

El nombre describe el caso, no el método. Una idea por prueba: si necesitas "y" en el nombre, son dos.

La misma estructura se llama también Given · When · Then (viene de BDD): given = arrange, when = act, then = assert.

pruebas junit 5 · 04

¿Qué verifica cada aserción?

aserciónpara qué
assertEquals(esp, real)Valores iguales. Con double, pasa una tolerancia: assertEquals(8.0, x, 1e-9)
assertTrue / assertFalseUna condición booleana
assertThrows(Ex.class, ...)Que el bloque lance esa excepción — y la devuelve para inspeccionar el mensaje
assertNull / assertNotNullReferencias
assertThrows(NoGradesException.class, () -> calculator.studentAverage(new Student("Mara", null)));
