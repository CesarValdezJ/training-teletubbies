GET/http/overview

¿Qué es HTTP?

HTTP (HyperText Transfer Protocol) es el protocolo de texto sobre el que habla la web: un cliente (navegador, app móvil, otro backend) envía una petición a un servidor, que responde con una respuesta. Es sin estado (stateless): cada petición se resuelve con lo que ella misma trae — el servidor no "recuerda" la anterior por sí solo.

GET/http/request-response

Anatomía de una petición y una respuesta

Petición
GET /books/42?fields=title,author HTTP/1.1 Host: api.biblioteca.com Authorization: Bearer <token>
Respuesta
HTTP/1.1 200 OK Content-Type: application/json { "id": 42, "title": "Cien años de soledad", "author": "García Márquez" }
  • Query params van en la URL (?clave=valor) — filtros, paginación, orden.
  • Body (cuerpo) viaja casi siempre en JSON — se usa en POST/PUT/PATCH, no en GET.
  • Headers llevan metadatos: autenticación, tipo de contenido, formato aceptado.
GET/rest/principles

¿Qué es REST? ¿Qué es una API?

Una API (Application Programming Interface) es el contrato que un servidor expone para que otros programas lo usen sin ver su código interno. REST (REpresentational State Transfer) es un estilo para diseñar esa API sobre HTTP.

Recursos como sustantivos/books, /books/42 — no /getBook ni verbos en la ruta.
El método dice la acciónLa URI identifica el recurso; GET /books vs POST /books dicen qué hacer con él.
Sin estadoCada petición trae todo lo necesario (ej. el token) — el servidor no guarda sesión entre peticiones.
RepresentacionesEl mismo recurso se puede entregar en distintos formatos — en la práctica, casi siempre JSON.
GET/architecture/request-flow

El recorrido de una petición GET /books/{id}

1
Cliente
arma la petición (URL, método, headers) y la envía por HTTP.
2
Controller
recibe la petición, valida su forma y la traduce a una llamada del dominio.
3
Service
aplica las reglas de negocio — no sabe nada de HTTP.
4
Repository / Model
obtiene o guarda datos (memoria, base de datos).

La respuesta sube por las mismas capas en sentido inverso: Repository → Service → Controller → Cliente. Cada capa solo conoce a la de al lado.

GET/architecture/mvc

MVC — Modelo · Vista · Controlador

ModelLos datos y las reglas del dominio: entidades, validaciones, lógica de negocio.
ViewLo que recibe quien consume la API. En REST no hay pantallas: la "vista" es el JSON de salida.
ControllerRecibe la petición HTTP y coordina entre Model y View — decide qué llamar y qué responder.

El patrón nació para interfaces gráficas; en una API REST se adapta: no hay HTML, pero la separación de responsabilidades es la misma idea.

GET/architecture/layers

Separación de capas — para qué sirve

Trace de una llamada
GET /books/{id} Controller → llama a BookService.findById(id) BookService → llama a BookRepository.findById(id) BookRepository → consulta la fuente de datos y regresa el objeto BookService → aplica reglas (ej. ocultar libros dados de baja) Controller → convierte el resultado a JSON y arma la respuesta HTTP
  • Cada capa tiene una sola responsabilidad: Controller habla HTTP, Service tiene las reglas, Repository habla con los datos.
  • Service se puede probar sin levantar un servidor HTTP ni una base de datos real.
  • Cambiar de almacenamiento (memoria → base de datos) no debería tocar la lógica de negocio.

Contrato de un endpoint

Path paramsid (integer, requerido) — identificador del libro
Query params— (no aplica en este endpoint)
Request body— (GET no lleva body)
Respuesta éxito200 { "id", "title", "author", "available" }
Errores404 no existe un libro con ese id

Diseñar el contrato antes de programar evita ambigüedad: qué entra, qué sale, y qué pasa cuando algo sale mal.
